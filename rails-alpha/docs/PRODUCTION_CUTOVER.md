# R-Rent Rails: production cutover runbook

**Current decision: NO-GO.** This tree is a Rails alpha, not a production candidate. `config/environments/production.rb` aborts production boot; `config/initializers/alpha_only.rb` rejects real operations; `bin/start-preview` is a synthetic-review entrypoint. Neither the SQLite nor the opt-in PostgreSQL staging path makes it safe for real renters. Do not remove those guards from this release to get it online. Prepare and approve a separate production revision. This document is a runbook, not a deployment or an approval.

**Source and destination:** The existing rental service was previously identified as AppDeploy at `rtpscrentalcars.com`. The requested Rails destination is `rtpsccarrentals.com`, a different spelling and not established by this runbook as owned, resolving or live. The gated Render review is a separate synthetic service, not a replacement or a migration source. Before touching routing, verify the actual active source host, application owner, authoritative datastore, destination domain ownership, DNS/TLS, hosting service, and the business owner's decision to retain or redirect the old hostname. Do not infer ownership from a redirect, certificate, matching brand, or code repository.

## 2. Inventory and reconcile the real service

1. Using owner-approved **read-only** access, map the live app/service snapshot, data ownership, schema, record identifiers, storage/files, time zones, provider references, and system of record for each category. Inventory vehicles and holds, future/active bookings, custody and overdue returns, unresolved incidents/maintenance, signed agreements/evidence, payments/deposits/refunds, and open queue work. Mark which systems are read-only references instead of writing replacements. If any source is unavailable or authority unclear, stop; do not use synthetic records to reconstruct it.
2. Draft and approve a versioned mapping with preserved source IDs, target IDs, required fields, date/time/currency conventions, collision rules and exception dispositions. Store protected records and mapping extracts only in owner-approved encrypted, access-logged storage with retention limits; no PII, filenames with identifiers, credentials, provider payloads or database dumps in Git, artifacts, tickets or chat. Commit only the importer, redacted schema notes and synthetic test fixtures. Never duplicate full card data or credentials. Retain required agreements/evidence in approved storage with access preserved, or document a verified read-only link.
3. Rehearse against an approved isolated recovery/staging datastore under realistic schema and permissions. Disable all outward jobs, bookings, money/custody effects and notifications during load; do not regenerate historical reminders, replay settled transactions or send onboarding messages. Import idempotently using source-system and source-record keys; quarantine invalid/unmapped records with access controls. Export a sanitized reconciliation: source/loaded/skipped/quarantined counts by category, date and status, overlap/conflict checks, assigned vehicles and active custody, financial amounts by currency/status, open obligations and sampled ID linkage. Compare provider-side financial state read-only where authorized; loading a record is not settlement. No unexplained discrepancy crosses cutover.

## 3. Controlled switch and validation

1. Name primary and fallback owners, freeze window, customer support process, approved DNS plan, stop thresholds, backup IDs and timestamps. Baseline old routes, data/queue and provider metrics. Preserve DNS records, including mail and domain verification; verify certificates and intended apex/www behavior ahead of switch where possible. Capture rollback record and DNS caching allowance.
2. Enter a write fence on the old app, let in-flight mutations drain, and record the last successful write and final export watermark. Stop legacy workers that could act on the target records. Capture consistent backup, import only the final delta after the same guarded rehearsal, and reconcile again. No concurrent writable sources; queued work remains quarantined until ownership is explicit.
3. Smoke the exact approved production revision on the destination before routing. Check hostname/TLS, authentication and roles, negative access controls, readiness/worker/audit, current data counts, open custody and availability, logs, cache rules and disabled side effects. Then switch only the approved routing. Confirm externally from more than one path and do not intentionally perform an actual charge, release, external send or real booking as a test without its separate approval.
4. Validate after routing: first watch data integrity, unknown/duplicate writes, bookings conflicts, availability/holds, signed-in role access, error and backlog spikes, auth/provider callback rates and support reports. Keep the legacy dataset available read-only under approved retention. Start separately authorized providers or worker effects one at a time only after readiness and evidence reviews. Review and sign after the first operational window and at the next agreed checkpoint.

## 4. Incident rollback

Pause new writes/outbox and external side effects immediately on unauthorized access, duplicate or unexplained financial activity, missing obligations, overlapping reservations, integrity drift, or material availability/auth failure. Preserve logs, outbox offsets and exact switch timestamp; notify assigned security, operations and reconciliation owners using approved channels. Before any new Rails writes, an approved routing reversal to the fenced legacy revision may suffice. **After Rails writes, do not simply re-open the old database:** fence both systems, inventory new activity and pending provider actions, reconcile/replay verified deltas under review, or use a validated forward fix. If restoring, use an isolated target and compare all post-backup actions before returning to service; never overwrite newer obligations blindly. Keep rollback routes private until owner approves a new GO decision. Record incident scope, control actions, unresolved cases, validation and actual recovery point/time.
